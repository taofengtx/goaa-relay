## 📌 規範 #12 升級 — 伸縮條款

**原規則**：所有檔案部署前必須 MD5 byte 級校驗。

**問題情境**：今天部署 config.yml 時，師兄手上的版本（Claude 交付 MD5 `3c8e83ae...`）跟 AiKa 在 DO 上實際寫入的（`144243b4...`）因 LF/CRLF 換行符 + Unicode 字元渲染差異而對不上，但**語義 100% 等價**。

**升級內容**：對 `yml / conf / ini / toml` 等被解析後丟細節的 server-side 配置檔，引入「**三重行為驗證**」作為 MD5 校驗的替代方案：

1. **工具語法驗證**（如 `cloudflared tunnel ingress validate`）
2. **邏輯模擬**（如 `cloudflared tunnel ingress rule <URL>`）
3. **實戰請求驗證**（如連續 20 次 curl）

三重通過即視為等價，**但必須立即將線上實際生效版本 sftp pull 回 git** 做新基準。

**約束**：`jsx / py / json / sh` 等被 build/import 的代碼檔**無此豁免**，仍須 byte 級 MD5。

## 🔬 雙 systemd 真兇深挖過程

今天最關鍵的工程偵察。記錄完整推理鏈，給未來窗口參考：

### 步驟 1: 表面症狀
```
api.goaa.ai/health           → 200 ✅
api.goaa.ai/workers/status   → 404 ❌
```

### 步驟 2: 第一層歸因（中午）
Cloudflare Tunnel 配置只把 hostname 路由到 OpenClaw:18789，**沒有 path-based 分流到 Model Router:8080**。
→ 新增 9 條 ingress prefix rules → 部署 → 仍然飄忽。

### 步驟 3: 怪事 — 同樣的 URL 有時 200 有時 404
- 本地 `curl http://127.0.0.1:8080/workers/status` → 200 ✅
- 公網 `curl https://api.goaa.ai/workers/status` → 50% 機率 404

### 步驟 4: 殺進程後又重生
- 手動 `kill <pid>` cloudflared standalone process
- 5 秒後新 pid 又出現
- → 不是孤兒進程，是 **systemd 在管它**

### 步驟 5: 找到第二個 service
```bash
systemctl list-units --type=service | grep cloudflar
cloudflared.service          loaded active running
cloudflared-tunnel.service   loaded active running   ← 兇手
```

兩個 service unit 都在 2026-05-11 05:29 創建，相隔 2 秒。

| Service | ExecStart | Restart |
|---------|-----------|---------|
| `cloudflared.service` | `--config /etc/cloudflared/config.yml tunnel run` | on-failure |
| `cloudflared-tunnel.service` | `tunnel run goaa-do-tunnel`（**無 --config**）| **always** (5s) |

### 步驟 6: round-robin 機制
兩個 cloudflared 進程都連到同一個 tunnel ID，Cloudflare Edge 視為 HA（High Availability）連接，**在兩個 connector 之間 round-robin 分配請求**：
- 分配到 `cloudflared.service` → 帶 ingress rules → `/workers/status` 路由到 :8080 → 200
- 分配到 `cloudflared-tunnel.service` → 無 ingress → 全部走預設到 :18789 → 404

### 步驟 7: 修復
```bash
systemctl stop cloudflared-tunnel.service
systemctl disable cloudflared-tunnel.service
# unit 檔保留（規範 #15）
```

### 步驟 8: 驗證
連續 20 次 `curl https://api.goaa.ai/workers/status` → **20/20 全 200** ✅

## 🎓 教訓 & 反思

1. **「殺進程」對 systemd 管理的服務無效**
   - 永遠先 `systemctl list-units | grep <name>` 看清全貌
   - 兩個 service 跑同一 tunnel 是 Cloudflare HA 設計，但是「**完整 config + 殘缺 config**」的雙開是隱性 bug

2. **「飄忽症狀」是雙進程或 HA 配置不對等的標誌**
   - 單次 curl 看不出，**連續 20 次測試**才能暴露 round-robin 行為
   - 規範 #15 的 stage-1 必含「功能回歸測試（20 次連測）」

3. **byte 級 MD5 對 server-side config 太苛刻**
   - YAML / conf 文件被解析後丟註釋、空白、引號樣式，**byte 不同但語義等價**很常見
   - 規範 #12 伸縮條款用「行為驗證」替代 byte 校驗，是工程務實主義

4. **AiKa 進化為真實工程合作夥伴**
   - 發現 cloudflared 讀 `/root/.cloudflared/` 而非 `/etc/`（自己改 systemd validate 路徑）
   - 發現 standalone 進程死灰復燃時主動排查
   - 路由模擬全綠仍 404 時不慌張，**先測本地 8080/18789 驗證 backend 沒壞**
   - MD5 不對也不卡死，**用 cloudflared validate + rule simulate + curl 三重行為驗證**
